01 · The Problem

飞书原生自动化只会做一件事：
"当 A 发生时，做 B"

一对一，一条线，一根筋。但你真正想做的是这样的：

订单确认了，查一下库存够不够。够就扣掉，不够就通知采购补货。 顺便每天下午给运营群发个汇总。 — 来自真实用户调研

一句话里有五件事：跨表查询、条件判断、数据修改、消息通知、定时任务。 飞书原生自动化一个都做不了。

bitable-orchestrator 让你用自然语言驱动这一切——跨表关联、条件分支、批量处理、事务回滚，一句话搞定。

02 · The Safety Pipeline

5 阶段安全管线
每一步都可暂停、可回滚

多维表数据是企业核心资产——直接改、错了就没了。 所以 bitable-orchestrator 不是"一句话就执行"，而是分成 5 个阶段， 每一阶段都给你看清楚 + 拍板的机会。

STAGE 01

意图解析

自然语言 → 结构化的"想做什么"（不是执行计划，是意图描述）。

STAGE 02

执行规划

查询路径、依赖图、原子操作序列。拓扑排序保证执行顺序正确。

STAGE 03

Dry-Run 预演

在不改数据的情况下，把每一行将要发生什么列出来给你看。

STAGE 04

原子执行

事务式执行——中途任何一步失败，全部回滚到执行前状态。

STAGE 05

审计学习

完整记录所有变更 + 失败原因，下次相似操作能复用经验。

03 · Key Design Choices

三件让 ToB 用户信任的事

① Dry-Run 预演必须显式——每一次破坏性操作前，强制展示"会动什么"。 不能让用户"以为只是查询，结果改了数据"。

② 原子回滚不是可选项——任何中途失败必须能回到操作前的状态。 飞书 OpenAPI 没原生事务，那就在 Skill 层模拟一个： 每次操作前记录原值，失败时按反向顺序还原。

③ 依赖图拓扑排序保证顺序—— "查库存→扣库存→通知采购"是有先后的，不能并行。 用有向无环图（DAG）建模操作依赖，拓扑排序后串行执行。

04 · What I Learned

三个"第一次"

做完 knowledge-healer 和 lark-survey-scoreboard 之后，我想刻意挑一个更偏 ToB / 更工程化的题目练手—— bitable-orchestrator 就是这次刻意练习的产物。它给我的"第一次"比另两个更多：

第一次设计多阶段安全管线——意图解析 / 计划生成 / Dry-Run 预演 / 用户确认 / 执行 + 回滚，五段全部可暂停、可回滚。 在此之前我做的 Skill 都是"输入 → 输出"一条线，不需要考虑中途出错怎么办。

第一次显式建模事务回滚——飞书 OpenAPI 没原生事务，那就在 Skill 层模拟一个： 每次操作前记录原值，失败时按反向顺序还原。这逼我去理解"事务"这个概念到底在保护什么。

第一次用拓扑排序做依赖管理—— "查库存→扣库存→通知采购"有先后依赖，不能并行。用有向无环图（DAG）建模操作依赖， 拓扑排序后串行执行。这是大学课程里讲过的算法，但第一次真的用上是在这里。

05 · The Problem It Solves

多维表批量编辑里
"误改难撤销"的真实问题

飞书多维表的批量操作 API 默认是"一旦执行，立即生效"。中大企业的业务表往往跨多张表、几千上万行记录， 一旦改错，撤销极其困难——飞书没有"全表 undo"，只能靠备份或人工回填。

bitable-orchestrator 在用户和 OpenAPI 之间插入一道缓冲层： 改之前先用 Dry-Run 看清楚"这次操作会动哪些行、改成什么"，确认后再真正执行； 执行过程中如果任何一步失败，按记录好的原值反向回滚。

对个人用户来说这层缓冲是"多此一举"——所以它没在 ToC 评审里胜出，这是合理的。 但对真正在企业里管几千行业务数据的人来说，这层缓冲就是"敢不敢用 AI 改表"的分界线。
