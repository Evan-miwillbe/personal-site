01 · The Meta-shift

做完 Multi-Agent 第 7 轮，
我发现一件有趣的事

Multi-Agent Research 做到第 7 轮时，我发现每一轮都在重复同一套循环： 读上轮经验 → 诊断瓶颈 → 选 1–2 个变量 → 跑实验 → 评估 → 决定保留或回退 → 写新经验。

这套循环同样适用于任何可编辑资产。

我也在反复踩同一些坑：水床效应（压缩 A 组件，B 组件膨胀）、 目标漂移（从"改进 skill"滑向"跑研究确认内容"）、 验证完成后该转型却继续验证。 换了任务，这些问题照样出现。它们属于长程自迭代本身的失败模式。

Multi-Agent 是我做的产品。
auto-new 是我做的"做产品的方法"。 — auto-new 设计动机

我把这套迭代方法做成了一个独立 Skill，叫 auto-new。 它接受任何 target 文件、任何 objective、N 轮实验。

02 · Four Paradigms

4 种实验范式
任务不同，实验设计也不同

auto-new 提供 4 种实验范式：

i · iterative

渐进迭代

适合架构演进。每轮改 1–2 个变量，小步快跑。
例：Multi-Agent v6.4 → v9.0。

ii · quantitative

参数扫描

适合超参数寻优。同一个任务跑不同参数。
例：MinerU PDF→MD 的 worker 数量寻优（3 worker 最优，11x 加速）。

iii · selective

候选筛选

适合从多个方案中选最优。生成 N 个候选，跑评估，挑最好的。

iv · verification

假设验证

适合证伪假设。Verifier's Rule：任务必须可验证才值得做。

03 · Sixteen Iron Rules

16 条工程规则
每一条都来自一次实际失败

这里列出其中几条：

架构 vs 参数 10–100x 杠杆差异
同样的时间，改架构的收益是改参数的 10–100 倍。优先改架构。
水床效应 · 全局核算
压缩 A 组件，B 组件膨胀。必须做系统级核算，不能只看局部。Multi-Agent R7 数据：Expert 省 13% / QualityReviewer 反增 21% / 系统总量几乎零。
噪声带协议
区分真实改进 vs 测量噪声。如果实验间差异 < 10%，可能是噪声，不要据此做决策。
Verifier's Rule · 可验证性预检
任务开始前，必须先回答"我怎么知道这个改动是改进还是变差?"。
L1 / L2 / L3 改进层级
L1 架构 / L2 行为 / L3 参数。先定位问题在哪一层，再改对应的东西。在 L3 改 L1 的问题，永远改不好。
跨 session 状态持久化
支持"睡前启动、醒来验收"的 batch 自主模式。

（完整 16 条见 GitHub 仓库 README。）

05 · Reflection

为什么我看重 auto-new

做 Multi-Agent 做到第 7 轮的时候，我发现自己每一轮在做的事其实是同一套循环。
把这套循环抽出来工程化，是我现在最感兴趣的方向。 — auto-new 设计动机

设计哲学融合： Karpathy autoresearch（单一可编辑资产 + 固定评估 + git 棘轮）、 TextGrad / GEPA（Nature 2025）的提示词优化范式、 ClawHub 社区的 Skill 设计实践。

auto-new 是我和 Claude Code 协作完成的第一个元层工具。 它目前最稳定的用户就是我自己：我用它迭代其他 Skill。它能否扩展到更广的场景， 还需要更多任务验证；现在可以确认的是，它在我的工作流里跑得通。
