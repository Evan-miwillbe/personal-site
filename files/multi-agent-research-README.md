# Multi-Agent Deep Research Framework

多 Agent 深度研究框架 — 基于 Claude Code 的虚拟研究团队。

**v9.0** | 453行 | 77 commits | 47轮实验(31验证+16消融) | 17个操作钩子全部验证通过 | 2 KEEP + 14 NOISE

> 输入一个题目，还你一份有数据支撑、有来源可查、经过交叉验证的研究报告。

## 为什么写这个文件

这份 README 记录了 v1 到 v9.0 的设计过程：改过什么、为什么改，以及哪些想法在实验里失败了。

整个 skill 从 v1.0 到 v9.0 经历了 77 次 commit、47 轮实验（31 验证 + 16 消融）、多次架构推翻重来。在这个过程中，用户并非全程在线。很多关键决策（为什么删掉 PM 层？为什么 handoff 是 200 字而非 500 字？为什么共识度<60%不是自动 debate？）的答案散落在对话历史中，如果不记录就会丢失。

本文件回答三个问题：
1. **每一步改了什么** — git commit 级别的事实
2. **为什么要这样改** — 是什么数据/失败/洞察驱动了这个决策
3. **为什么下一步去了那个方向** — 因果链，从一个发现到下一个实验

## 术语小词典（先看这里）

读这篇文章会反复碰到的概念，用日常类比解释：

| 术语 | 类比 | 一句话解释 |
|------|------|-----------|
| **Token** | AI 的"思考预算" | AI 处理的最小文字单位。每次对话消耗 token 就像花钱——花完就停。一个中文字≈1.5 token |
| **Context Window** | AI 的"工作台" | AI 一次能同时看到的信息量上限。像一张桌子——放太多纸就会掉到地上看不见 |
| **Spawn** | 派遣新员工 | 主 AI 创建一个新的子 AI 去执行特定任务。像经理分派工作给组员 |
| **Agent** | 虚拟员工 | 一个被分配了特定角色和任务的 AI 实例。可以独立搜索、思考、写作 |
| **Handoff** | 交班条 | Agent 完成任务后写的精简交接报告，给下游接手者看。像夜班护士留给白班的交接条 |
| **Context（上下文）** | 当前脑子里的东西 | AI 此刻能"看到"的全部对话历史和资料。超出范围的它就忘了 |
| **SAS / MAS** | 独奏 vs 乐队 | Single-Agent System = 一个 AI 独立完成；Multi-Agent = 多个 AI 分工协作 |
| **p^n** | 接力赛出错率 | 如果每棒 90% 成功，5 棒连跑成功率 = 0.9⁵ = 59%。环节越多，整体越容易出错 |
| **DPI 定理** | "人多不一定力量大" | Stanford 论文证明：给同样的思考预算，一个人专注做 ≥ 一群人分着做。除非任务真的太大 |
| **Lost in Middle** | 三明治效应 | AI 和人一样：读长文时开头和结尾记得清楚，**中间部分系统性忽略**。很像考试只记第一题和最后一题 |
| **Gate** | 质检关卡 | 流程中的检查点——不达标就不放行。像工厂流水线上的质检站 |
| **Heartbeat** | 心跳信号 | Agent 定期汇报"我在做什么/发现了什么/下一步去哪"。像潜水员每隔一段时间拉一下绳子 |
| **One-shot** | 一次性任务 | 执行完就退出，不能持续运行。像叫外卖——送到就结束，不会留下来帮你刷碗 |
| **跨授粉** | 串门聊天 | 把 A 组发现的关键信息传给 B 组。像不同研究室之间分享最新进展 |
| **覆盖审计** | 查漏补缺 | 检查所有 Agent 合起来是否覆盖了题目的所有方面，有没有盲区 |
| **评估漏斗** | 分诊台 | 小问题快速扫一眼，可疑的仔细查，严重的全面检验。不是每个 claim 都值得花同样精力去核实 |
| **共识度** | 投票一致率 | 多个 Agent 对同一问题的回答有多一致。>80% 说明结论可信；<60% 说明有分歧需要解决 |
| **Commit** | 存档点 | 代码的一次保存记录，像游戏里按了存档。可以随时回溯到任何一个存档点 |
| **Foundations** | 理论资料室 | 存放"为什么这样设计"的详细论证。日常运行不需要，但回头查原因时必看 |

## Phase 1: 初始框架到学术升级 (v1.0-v3.1, 4/23-4/28)

> **读前提示**：下文用 `反引号代码` 标注的字母数字串（如 `b7231bb`）是 git commit 编号，可以用它在代码仓库中定位对应修改。

### v1.0 `b7231bb` — 从零开始

起点是腾讯老师的一次语音分享。我从中留下了三个做法：Agent 用文件交换信息；每个角色只负责一类任务；流程按阶段推进。这三点从 v1 一直保留到 v9.0。

最初设计：PM 中心制（一个"项目经理"AI 统管全局），7 个 Agent，5 个 Phase。

### v2.0 `0d40206` — 12 篇论文的冲击

**为什么做**：v1.0 主要靠直觉设计。读完 12 篇论文后，我发现其中不少判断站不住脚。例如 Stanford 的 DPI 定理表明：**思考预算（token）相同时，一个 AI 专注完成任务的效果不低于多个 AI 分工**。

> 💡 **类比**：就像一个资深记者花 8 小时写一篇深度报道，通常比 4 个实习生各花 2 小时拼出来的更好——除非这个选题真的需要 4 个人分头跑不同现场。

**关键发现与对应决策**：
- Stanford DPI 定理 → 不再默认多 Agent，先判断"真的需要拆分吗？"
- CORAL 36%继承率 → 一个 Agent 的发现有 36% 会被其他 Agent 复用，所以要主动分享（跨授粉）
- WideSearch 召回瓶颈 → 内容质量再高，如果有整个子话题没搜到就白搭，要做覆盖审计
- AlphaEvolve 评估漏斗 → 不是每个小事实都要花大力气核实，先快速扫，可疑的再深挖
- BrowseComp Best-of-N → 对有明确对错的问题，让 3-5 个 Agent 独立回答后投票比信任任何一个更准

从这一版开始，设计决策必须能追溯到论文或失败记录，不能只靠"我觉得应该这样"。

### v3.0 `338c34e` — 自迭代机制诞生

**为什么做**：清华刘奕好演讲提到"7949 agents，15% 成功率"——多 Agent 不是银弹。关键不是设计得多复杂，而是**能从失败中学习**。

**关键决策**：创建 `learning-history.md`。每次研究结束后，记录流程哪里需要改进，而不是复述研究结论；下次启动时先读这些记录。这样，skill 可以跨项目保留工作方法上的经验。

同时引入**可靠性数学**（p^n 模型）：

> 💡 **类比**：假设每个 Agent 的单步正确率是 90%。5 个 Agent 串联后，整体正确率只有 0.9⁵，也就是 59%。每多一次交接，就多一次出错机会。这组计算直接限制了后续版本的 Agent 数量上限。

## Phase 2: 理论膨胀与崩溃 (v4.0-v4.3, 4/28-4/29)

### 为什么会膨胀

v4.0-4.2 连续引入各种高级机制：四支柱架构、三方辩论、级联评估、跨授粉、上下文工程规则... 每个单独看都有道理（都有论文支撑），但组合起来让 SKILL.md 从 600 行飙到 1200 行。

> 💡 **类比**：就像一份菜谱，原本写"放盐少许"就够了，你非要加上"盐的化学原理"、"不同盐的产地对比"、"最优放盐时机的论文"——知识都对，但厨师看不到"下一步该干啥"了。

**理论本身没有错，但数量太多，执行指令被淹没了**。

### v4.3 `7f1ef27` — "团队组不起来"

这是整个项目最关键的转折点。

**现象**：框架运行时，主 AI（下文简称"主 CC"）本应派遣其他 Agent，实际却独自完成搜索和写作，没有执行分派任务的指令。

**根因分析**（为什么主 CC 会"叛变"？）：
1. 文件开头没有明确写"你的**第一步**是 spawn 团队，不是自己动手"
2. "主 CC"和"PM"的职责写得太像，AI 分不清自己该做啥
3. **最致命的**：关键指令"spawn PM"被埋在第 711 行——而 AI 的工作台（context window）可能在第 500 行就塞满了，根本没看到那条指令

> 💡 **类比**：这就像你给新员工一本 700 页的操作手册，关键步骤"先开机"写在第 711 页。员工看完前 500 页就开始凭直觉干活了——不是不听话，是真的没看到。

**修复是正确的**（加了启动序列、检查关卡等），**但代价是 +28% 膨胀到 1382 行**——让文件更加不可维护。

**教训（影响了后续所有版本）**：增加指令数量并不能保证执行，文件越长，关键要求越容易被漏掉。问题需要在**架构层面**解决。v6.0 后来把文件从 1382 行压到 221 行，并把关键指令放进前 50 行。

## Phase 3: 精简与再膨胀 (v5.0-v5.5, 4/30-5/2)

### v5.0 `91bf00b` — 大精简

1382→647 行（-53%）。5 个决策框架合成 1 张决策图，50 条原则压到 15 条，参考文件从 31 个减到 13 个。文件清爽了很多。

### 为什么又膨胀回去（"过度断舍离"后遗症）

v5.0 精简后开始拿去跑真实项目（泳池机器人出口策略、积极心理学、Token 节省研究），每个项目都踩到了精简时扔掉的某个"边界条件"——就像搬家后发现把充电器扔了：

| commit | 来源项目 | 发现的问题 | 加入的补丁 |
|--------|---------|-----------|-----------|
| `f5e80e0` v5.2 | 积极心理学+Token节省 | spawn后30s不检查=静默失败；跨Agent参数不统一 | 心跳30s/共享参数/Phase 2.5 |
| `6f8f8b6` v5.3 | 跨4个项目重复 | Phase Gate被跳过4次；进度不同步4次 | 并发≤5/Phase Gate铁律 |
| `22479d6` v5.4 | — | PM不理解课题就分板块→板块边界错 | PM领域摸底前置 |
| `77e255f` v5.5 | — | 精简丢失了三方辩论/四支柱/Agent自检等有价值内容 | 恢复7个reference文件 |

**647 行重新膨胀到 893 行**。每一行都是某个项目踩坑后加的。

**驱动 v6.0 重写的判断**：问题不在指令数量，而在**架构**。当时确认了三个根因：

1. **PM 二级 spawn 不可靠**——就像经理叫秘书去招人，秘书招到人后和经理的通信经常断线（Windows 上 socket 层问题，4 个项目全失败）
2. **CLO（学习记录官）无法持续运行**——当前框架是 one-shot 的（做完即退出），不能让一个 Agent 在旁边"一直观察"
3. **全量加载浪费 token**——每个 Agent 启动时都要读一遍 893 行的完整文件，其中 80% 跟它的任务无关

**结论**：再多补丁也救不了一个错误的架构。需要重建。

## Phase 4: 架构重构 (v6.0-v6.4, 5/3)

> **本章核心**：这是整个框架的"推倒重来"时刻。如果前面是在一间布局有问题的房子里不断加家具，v6.0 就是把房子拆了按新图纸重盖。

### v6.0 `6605934` — 从根因修复

不再打补丁。直接重写架构：

```
v5.x（旧架构，像公司层级）:
  主CC(董事长) → PM(总经理) → Expert(员工)×N / Explorer / FactChecker / Critic / Synth
                              → CLO(旁听记录员，但总是中途离开)

v6.0（新架构，像工作室扁平制）:
  主CC(老板兼PM) ─┬─ Expert(研究员)×N
                   ├─ QualityReviewer(质检+批评合一)
                   └─ Synthesizer(执笔人)
  主CC自己兼任：记录员 + 关卡检查
```

**为什么消除 PM（裁掉中层管理）**：4 个项目中，"主CC→PM→Expert"这条两跳链路在 Windows 上都发生了断线。改成主 CC 直接管理 Expert 后，只剩一跳，通信稳定了。

**为什么合并 FactChecker + Critic（两岗合一）**：两个角色的工作内容重叠超过 50%，都在读报告并找问题，分开执行多花约 5 分钟。合并后的 QualityReviewer 依次核实数据、检查逻辑、给出修改建议，效果相同，耗时更短。

**为什么 CLO 不再是独立 Agent**：当前框架采用 one-shot，Agent 完成任务后就退出。连续 3 次实验里，CLO 都无法持续观察全程。最后把记录工作交给始终在线的主 CC。

**数据**：893→221 行 / 运行时 token 消耗 -80% / 角色从 9 个减到 4 个 / 流程从 7 步减到 4 步。

### v6.3 `f0dc563` — SKILL.md 自包含

protocols/ 文件夹里约 200 行内容与 SKILL.md 重复。删除后，主 CC 启动时要读取的内容从约 756 行降到 213 行（-72%），关键指令也更容易被看到。

### v6.4 `4b66017` — foundations/ 解决"精简即丢失"

**问题**：v5.0 精简丢知识 → v5.5 找回来 → v6.0 又精简掉... 这个"断舍离-后悔-买回来"的循环没完没了。

**解法**（v9.0 继续沿用）：把知识分成三层：

- **SKILL.md**（~200行）= **操作手册**：告诉 AI "做什么、按什么顺序做"。运行时加载。像厨房里贴的菜谱。
- **roles/**（~500行）= **岗位说明书**：每个 Agent 只读自己那份。像新员工入职只看自己岗位的手册。
- **foundations/**（~2080行）= **理论资料室**：所有的"为什么这样设计"。**运行时永不加载**（AI 不需要知道为什么，它只需要照做）。供人类阅读理解、以及未来重构时参考。

这样，操作手册可以保持精简；理论资料在需要时再查，不会一直占用 AI 的 context。

## Phase 5: 优化实验 (v7.0-v7.5, R1-R11, 5/3)

> **本章核心**：前四个阶段解决架构问题。从这里开始，架构保持不变，只调整交班条长度、质检深度等参数。

### 为什么开始做受控实验

v6.4 完成后，大方向稳定了，但很多具体参数还是凭直觉定的——交班条（handoff）多长合适？质检要多深？最终执笔人要不要单独请人？交叉验证值不值得花那个钱？

**方法**：固定研究主题"积极心理学的发展（2015-2025）"，每轮只改一个参数，再记录 token、报告质量和运行时间。用控制变量判断每次调整是否有效。

### R1 (v6.4 Baseline) — 建立基线

> **注**：P0 = 严重错误（必须修复，如数据错误）。A+B = 高质量来源（A=一手论文，B=权威综述）

| 指标 | 数据 | 类比 |
|------|------|------|
| 总 token | 217K | 花了21.7万个"思考单位" |
| 报告字数 | 5,654 | 约3页A4纸 |
| P0 | 2（QR修复） | 2个严重错误被质检发现 |
| QR token | 67.5K | 质检员一个人花了总预算的31% |
| 耗时 | ~26min | — |
| 来源质量 | 100% A+B | 所有引用都是高质量来源 |
| Agent存活率 | 4/4 | 没有人中途"死机" |

**观察**：顺风局下运行良好。但质检员(QR)是最大的 token 消耗者——花了 67K 却只找到 2 个错误。如果能让研究员(Expert)自己在交稿前就检查一遍，质检员的工作量就能大幅减少。

> 💡 **类比**：就像工厂发现质检站发现的 bug 其实工人在工位上就能自查出来——让工人多花 5 分钟自检，比质检站花 30 分钟全检更划算。

**→ 决定下一步**：给 Expert 加自验证步骤，让错误在源头被消灭。

### R2 (v7.0): 源头治理——自验证消灭 P0

**现状**：R1 证明 QR 花了最多预算但只修 2 个 P0。这 2 个错误（数值偏差、年份错误）其实是 Expert 在写报告时就能自己发现的。

**改动**：Expert 报告写完后新增"2.5 自验证阶段"——自己回头检查一遍数据和引用。同时从 4 板块增加到 5 板块（加入"批判"视角），字数从 5000 提到 7200。

**结果**：

| 指标 | R1 | R2 | 变化 |
|------|-----|-----|------|
| P0 | 2 | **0** | 完全消除 |
| 报告字数 | 5,654 | 7,200 | +27% |
| 来源数 | 35 | 46 | +31% |
| Token | 217K | 269K | +24% |

**结果**：让 Expert 交稿前自查，比把错误全部留给下游质检更有效。此后的实验中，P0 没有再次出现。

**意外发现**：QR token 几乎没变（67K→66.5K）——即使不需要修 P0 了，QR 读报告本身就要花那么多 token。这暗示 QR 的成本瓶颈不是"修错"而是"读全文"。

**→ 问题**：既然 P0 已经消除，QR 还需要逐条核验吗？能不能只抽样检查？

### R3 (v7.1→v7.2): QR 精简 + Handoff 压缩——两个实验一轮做

**改动 1**（`626e7de` v7.1）：QR 从"逐条核验每个数据点"改为"每板块抽样 3 个关键点 + 跨板块一致性检查"。

**改动 2**（`08a8969` v7.2）：Handoff 从 ≤500 字改为 150-200 字。

**结果**：QR 从 66.5K 降到 53.7K（**-19%**）。Handoff 压缩后信息传达质量不降反升。

**为什么是 150-200 字，而不是 100 或 300**：实验中，200 字交班条和 500 字版本的信息传达效果相同；低于 100 字后，关键数据开始丢失。压缩迫使研究员删掉客套话和背景铺垫，只保留真正影响下游判断的内容。

> 💡 **类比**：想象你要把一本 300 页的书的精华传达给同事。写一页摘要（200字）比给原书（500字节选）更有效——因为你被迫筛选出最重要的 5 个点，同事读完印象更深。但如果只让你写一句话（100字），关键数据就会被牺牲。后来 LightThinker 论文也证实了这个规律：压缩 70% 内容后，下游质量反而提升了 2.42%。

**→ 问题**：QR 虽然省了，但它还在做"横向穿透"（跨板块对比分析）时出了精度问题——主 CC 凭记忆写的对比数据偶尔记错。谁来做这件事更合适？

---

### R4 (v7.3): 横向穿透职责迁移——把活分给最合适的人

**现状**：主 CC 在综合阶段写"各板块对比分析"时，因为是凭记忆引用数字，出现了 2 处精度错误（百分比记混了）。

**改动**（`9208ba7`）：横向穿透从主 CC 迁移给 QR。QR 本来就要阅读全文做质检，可以直接对照原文引用数字。

**结果**：Token 总量从 249K 涨到 324K（+30%）——但这主要是搜索波动（Expert 这轮碰到了更多论文），不是横向穿透本身贵了。关键收益：精度错误归零，第一性原理分析质量显著提升。

**两次修复**（`2b8ca27` + `6aff2b3`）：第一版迁移时不小心丢了"讨论板输入"和"learning-log 同步"，两次 commit 补回来。

> 💡 **教训**：迁移职责时容易只搬"主功能"而漏掉"附带功能"。每次迁移后要检查：原来这个人还顺手做了什么其他事？

---

### R5 (v7.4): Synthesizer 轻量化——验证"不读原文也能写好"

**现状**：Synthesizer（执笔人）在 spawn 后会读全部板块报告（每篇 3000-4000 字 × 3 篇 = ~10000 字输入），花 58.7K token。但它已经有 handoff（每篇 200 字精华）+ 横向穿透（跨板块对比），这些够不够？

**假设**：如果 handoff 质量够高（R3 已验证），Synthesizer 不需要读原始素材。

**改动**（`f4277f9`）：Synthesizer 只读 handoff + 横向穿透 + QC 报告，不读原始板块报告。

**结果**：Synthesizer 从 58.7K 降到 40.5K（**-31%**），报告质量不降甚至信息密度更高。

**意外发现**：不读原文反而迫使 Synthesizer 做更多原创综合（因为它不能直接"复制粘贴"素材，必须自己组织逻辑）。设置了一个"按需深读"机制（如果 handoff 信息不够可以回读原文），但**从未被触发**。

---

### R6 (v7.5): 消灭 Synthesizer——主 CC 自己就是最好的执笔人

**现状**：R5 证明 Synthesizer 只需读取 handoff 和横向穿透。主 CC 管理全程后，context 里已经有 handoff、横向穿透和 QC 结果，再 spawn 一个角色只会重复传递信息。

**改动**（`a866f11`）：默认由主 CC 直接写最终报告。Synthesizer 降级为"context 快满时的备选方案"。同时 QR 增加"数据附录"——把所有关键数字汇总为一张表，作为主 CC 综合时的"弹药库"。

**结果**：省 ~40K tokens + 5 分钟 spawn 时间。报告质量不降（主 CC 有完整上下文，精度更高）。

**意外发现**：跑这轮时网络中断了一次，但本地 spawn 的 Agent 全部不受影响继续运行——验证了扁平架构的鲁棒性。

**结论**（`993079a` 同期）：同时写入了"证据透明度规则"——要求报告中对有争议的数据明确标注方法论分歧的来源，不用模糊的"范围区间"来掩盖不确定性。

### R7: 水床效应的发现——系统优化≠局部优化之和

> 💡 **这一轮学到的道理适用于所有优化问题：压低一个环节，另一个环节可能被"挤"上去。**

**现状**：Expert 报告写得很长（4000-5000 字），有大量"本章将讨论..."之类的过渡段。直觉：换成结构化格式（核心发现/证据链/争议），去掉废话，应该能省 token。

**假设**：结构化格式 → Expert 省 ~13% token → 系统总量也省 ~13%。

**实验**：Expert 报告从"叙事型"改为"结构化证据型"，字数目标从隐性 5000 改为显性 3000。

**结果（意外）**：

| 角色 | 变化 | 解释 |
|------|------|------|
| Expert 总量 | **-13%**（145K→127K） | 假设成功：结构化确实省了输出 |
| QR | **+21%**（57K→70K） | 意外：验证工作量反而暴增 |
| 系统总量 | **-3%**（只省了一点点） | 远低于预期的 -13% |

**为什么 QR 会增加？**

> 💡 **水床效应**（waterbed effect）：把水床一头按下去，另一头翘起来。
>
> Expert 写得更精炼 → 每句话都是数据点 → QR 需要验证的点从 35 个变成 47 个 → QR token +21%。数据密度提高了，但验证工作量也等比上升。

**R7 的教训**：优化一个环节时，要同时看它对**下游**的影响。研究员少写 13%，质检员却多花 21%，系统总量几乎没有变化。

**精细化融入**：结构化格式本身是好的（信息密度确实更高，报告质量更好），所以保留。但**不把它当作"省 token"的手段来宣传**——它的价值是质量提升，不是成本节省。下一步需要同时优化 QR 的验证策略才能实现系统级节省。

### R8-R9: 交叉验证到底值多少钱？（成本-质量的精确定价）

**现状**：研究员之间各做各的，互不参考对方的发现。直觉：如果让他们互相看看对方的成果再补充搜索，应该能发现"单独一个人看不到的盲区"。

**假设**：交叉验证（Phase 1c）→ 更多独到洞察 → 报告质量提升。但要花多少代价？

**R8（无交叉，对照组）**：199K tokens，产出标准质量报告。

**R9（全交叉，实验组）**：每个 Expert 读完其他两人的 handoff 后做一轮补充搜索。

**R9 结果**：
- Token：329K（**+65%！比无交叉贵了 2/3**）
- 新发现：+5 个**深度洞察**（如"CLPM 方法论下虚假效应概率 100%"——这个发现直接改变了理论章节的核心论证）
- 这些洞察在 R8 中**完全不存在**——它们只能通过跨板块视角才能被发现

**用户在此时的关键判断**：

> "这不是'要不要做'的问题，是'什么情况下值得做'的问题。"

具体来说：
- **科普类研究**（目标是通俗概述）：+65% 成本换 5 个深度洞察，ROI 偏低 → **可选**
- **学术类研究**（目标是原创贡献）：这 5 个洞察可能就是论文的核心贡献 → **必须**

**→ 问题**：有没有办法用更低成本获得**部分**交叉验证的好处？

---

### R10: 80/20 法则——用 10% 成本达到 80% 效果

**假设**：与其让 Expert 做完整的补充搜索（耗 token 巨大），不如让他们在 handoff 中写下"我想问其他板块的 2-3 个问题"——把**提问权**给 Expert，把**回答权**给 QR（反正 QR 要读全部报告）。

**实验**：Expert handoff 末尾新增"想问其他板块的问题"（每人 2-3 个，总计 9 个问题）。QR 在横向穿透时带着这 9 个问题去分析。

**结果（精确对比）**：

| 维度 | R8(无交叉) | R9(全交叉) | R10(轻量交叉) |
|------|-----------|-----------|-------------|
| Token | 199K | 329K(+65%) | 218K(**+10%**) |
| 跨板块关联数 | 3 | 4+ | 4 |
| 跨板块矛盾数 | 2 | 3 | 3 |
| 深度洞察 | 0 | 5个 | 2个深度+3个浅层 |

**成本增加 10%，达到全交叉约 70% 的效果**。QR 带着明确问题做横向分析，比没有方向地寻找关联更省时间。

> 💡 **可复用的原则（80/20 法则在信息工作中的具体化）**：在任何需要"跨领域整合"的工作中，与其让每个人都全面了解其他人的工作（成本极高），不如让每个人提出"我对其他领域最想知道的 2-3 个问题"（成本极低），然后让一个全景视角的人（这里是 QR）统一回答。

### R11: 选择性投入——不是所有板块都值得做交叉

**现状**：R10 的轻量交叉对所有板块一视同仁。但直觉上，有些板块是"自包含"的（比如"某疗法 vs 某疗法的头对头比较"——它的结论不需要其他板块的信息来丰富），有些板块天然需要跨领域视角。

**假设**：如果能准确预判哪些板块值得做交叉、哪些不值得，就能进一步省成本。

**实验**：3 个板块中，只对 2 个"高 ROI"板块做 Phase 1c 补充搜索，跳过 1 个"自包含"板块。

**ROI 判断标准（在实验前做出预判）**：
- 理论演变 → HIGH（天然需要实证数据验证理论预测）
- 批判反思 → MEDIUM（方法论批判需要具体案例支撑）
- 实践干预 → LOW（效果量对比是独立实证叙事，不依赖其他板块）

**结果**：
- 省下 ~19K tokens（跳过的那个板块在 R9 中花了 34K）
- 最终报告**无可感知的质量缺口**——被跳过的板块内容完全由 Phase 1a 覆盖
- 被选中的两个板块通过 Phase 1c 产出了**改变核心论证的关键发现**（CLPM 虚假效应 + MYRIAD 致害数据）

**更重要的发现**：实验前的 ROI 预判和实验后的实际价值**完全一致**。这说明：在研究开始时，一个有全景视角的人（主 CC）可以可靠地预测哪些方向值得加大投入。

> 💡 **可复用的原则**：不是所有方向都值得同等投入。在投入前先做 ROI 预判——问自己"这个板块从跨领域信息中能获益多少？"如果答案是"它自己就能讲完整个故事"，就不用花资源做交叉。省下的资源投到"天然需要跨领域视角"的方向上。

### R7-R11 的方法论总结（为什么这段值得反复读）

这 5 轮实验最后整理成一套迭代步骤：

```
1. 观察现状 → 发现"不舒服"的点（成本高/质量低/效率差）
2. 提出假设 → "如果做X，应该能改善Y"
3. 最小实验 → 只改一个变量，测量前后对比
4. 分析结果 → 不只看"假设验证了吗"，更要看"有什么意外发现"
5. 精细化融入 → 不是粗暴地"用新方案替换旧方案"，而是：
   - 好的部分写入 SKILL.md（操作层）
   - 原理写入 foundations/（知识层）
   - 适用条件写清楚（不是万能的，什么时候用什么时候不用）
6. 下一个问题 → 基于本轮发现，自然引出下一轮要验证什么
```

每一轮的"意外发现"往往比"预设假设的验证"更有价值：
- R7 的假设是"结构化省 token"，意外发现是"水床效应"
- R10 的假设是"轻量交叉有效"，意外发现是"提问比搜索更高效"
- R11 的假设是"跳过低 ROI 板块无损"，意外发现是"ROI 可提前准确预判"

这套步骤后来也被我用在其他需要反复迭代的任务上。

### 优化期的因果链总结

> 下面按因果顺序列出 R1 到 R6。后一轮都在处理前一轮暴露的问题：

```
R1 发现质检员(QR)花了总预算的31%却只找到2个错误
  → R2 让研究员(Expert)自己检查一遍 → 严重错误直接归零
    → R3 质检员可以只抽样检查了 + 交班条可以只写200字
      → R4 发现主CC凭记忆写"各板块对比分析"时记错了数字
        → R4 这活交给质检员做(它本来就要读全文，数字不会错)
          → R5 既然质检员已做了对比分析，执笔人只需读交班条
            → R6 既然执笔人只读交班条，主CC自己也能直接写——不需要另请执笔人了
              → v7.5: 从派遣4种角色变成了只需2种(研究员×N + 质检员)
```

从 R1 到 R6，角色减少是实验结果：信息不需要经过某个角色时，就删除那一层转交。

## Phase 6: 学术回溯重整合 (v8.0, R12-R31, 5/4)

> **本章核心**：前面的压缩把文件减到 370 行，也误删了 17 个有论文依据的机制。这个阶段逐一把它们放回实验，只有测到效果才保留。

### 为什么要回溯

v7.5 精简到了 ~370 行，执行效率很高。但回头对比 v2.0-v4.2 的设计，发现**17 个有学术证据支持的操作机制被历次精简丢失了**：

- Heartbeat（CORAL 验证有效，禁用后 -18.6%）→ v6.0 简化时被删
- 覆盖审计（WideSearch 证明必要）→ foundations/ 有，SKILL.md 无钩子
- 跨授粉注入（CORAL 36%继承率）→ foundations/ 有，SKILL.md 无钩子
- Token 经济学决策（DPI 定理）→ 整个 repo 不存在
- 共识度检查（Self-Consistency >80%=可信）→ 不存在
- ...

这些机制有论文数据支持，只是在历次压缩中被当成冗余删掉了。

### 为什么选择"每轮+1个小模块"

两个选择：
- A) 一次性加完 17 个模块（快，但无法验证哪个有用哪个是噪音）
- B) 每轮加一个，跑完整研究验证（慢，但每个模块都有实战数据）

选了 B。理由：v4.0-4.3 的教训是"看起来对的东西组合起来可能灾难"——1200 行全是"有道理"的内容，但组合起来 AI 根本不执行。逐个验证确保每一行新增都有实战支撑。

> 💡 **类比**：就像装修房子加家具——不是一次买 17 件往里塞（可能放不下/风格冲突/动线堵塞），而是一件件加，每加一件就住两天看看舒不舒服。不舒服就退回去。

### 每一轮的标准流程（理解 R12-R21 的阅读框架）

每一轮遵循相同的"假设驱动实验"模式：

| 步骤 | 做什么 | 为什么 |
|------|--------|--------|
| ① 选择 | 从 17 个候选中选 ROI 最高的下一个 | 先验证最有可能有用的 |
| ② 设计 | 写 ≤15 行新规则到 SKILL.md | 最小改动，不影响已有流程 |
| ③ 融入 | 找到规则在现有流程中的准确位置 | 不是加在末尾，是嵌入正确的 Phase/Step |
| ④ 构造验证场景 | 设计能触发新机制的主题/板块配置 | 不是"跑一次看看"，是主动创造条件 |
| ⑤ 跑完整研究 | 同一个主题(积极心理学)不同子方向 | 控制变量：只有新增规则是不同的 |
| ⑥ 观察 | 新机制是否被触发？是否误触发？ | 既要验证"能响"，也要验证"不该响时不响" |
| ⑦ 微调 | 根据实验结果调整措辞/阈值/条件 | 第一版往往不够精确 |
| ⑧ 记录 | 写入 learning-history + commit | 所有改动有据可查 |

### 每轮的决策逻辑

#### R12 `424d455`: 跨授粉注入

**为什么先做这个**：CORAL 论文数据最强（36%继承率，17%改进率），且解决了一个已知痛点——板块之间信息隔离导致重复搜索和口径不一致。

**设计选择**：≤100 字精炼（不是完整 handoff），注入 spawn prompt 开头。为什么开头？因为后面 R16 会验证 Lost in Middle 效应，但此时已经有直觉——关键信息要放前面。

**结果**：P0=0，口径问题仅 5 条（之前的项目动辄 10+）。理论板块的"效果量坍缩链"被循证板块主动引用。

**额外发现（实验中的"意外收获"，比原假设更有价值）**：

原计划是"并行 spawn 3 个 Expert，彼此注入对方的 handoff"。但跑起来才发现一个逻辑bug——并行的 Agent 同时在跑，彼此的 handoff 都还不存在（都没完成呢），怎么注入？

**解法（序贯策略）**：先 spawn 1 个 Expert 跑完 → 拿到它的 handoff → 提炼 ≤100 字 → 注入给后续 2 个 Expert 的 spawn prompt → 然后再并行跑这 2 个。

这增加了 ~7 分钟（等第 1 个跑完），但带来了三板块间逻辑一致性的显著提升。**有时候"稍微慢一点"反而是最优解**——比所有人同时开始但互相不知道对方在做什么要好。

> 💡 **可复用的原则**：多人协作不一定要"全部同时开始"。如果后续任务需要前置知识，那"先跑一个→分享发现→再并行其余"（序贯-并行混合）可能比"全部并行→事后拼接"更高效。这在团队管理中也是一样的。

**→ 下一步**：既然跨授粉通过了 Phase 1，接下来验证 Phase 1→2 之间的 Gate 机制——"完成了"不等于"完成得好"，怎么判断质量够不够进入下一阶段？

#### R13 `95656fa`: 覆盖审计 Gate 1.5

**为什么做**：WideSearch 论文说"召回是瓶颈(80% F1 but <20% SR)"——即使每篇内容质量高，覆盖不全 = 报告有盲区。

**设计**：Expert 全部完成后，主 CC 汇总 handoff 检查三项：A/B≥60%？核心 claim≥3独立源？子主题全覆盖？

**测试方法**：故意给板块 03 极窄范围（仅"复制危机+开放科学"），看 Gate 1.5 能否检出。

**结果**：正确检出 3 个缺失维度 → 触发补充 Expert → 覆盖度从 ~40% 提升至 ~95%。

**意外发现**：当所有板块都 confidence:H + A/B>80% 时，Gate 1.5 自然 pass（30 秒扫描）。它的价值是**安全网**而非常规触发——主要在 Expert 偏离范围或文献比预期稀疏时才真正起作用。

**→ 下一步**：Gate 验证了，现在回到 S0 层面——Token 经济学决策框架，从源头控制 Agent 数量。

#### R14 `ab76150`: Token 经济学 + 2-Agent 最优配置

**为什么做**：R12 用了 4 个 Agent，R13 用了 3 个。到底几个 Agent 才是最优？DPI 定理说"等 token 下 SAS≥MAS"，但研究任务不是等 token 的——是等**覆盖度**的。需要一个净收益公式。

**设计**：MAS净收益 = 并行探索广度 + 知识复用 − token成本 − 同步误差 − 交接损耗。三档决策：<20%→SAS / 20-50%→MAS≤3 / >50%→MAS 3-5。

**验证方法**：用这个框架做决策 → 选择 2 Agent（正交板块：剂量效应×组织应用），主 CC 自己做 QR。

**结果**：报告 13,738 字符（>R13），token 仅 ~110K（vs R13 的 177K = **-38%**）。质量不降甚至略升（主 CC 做 QR 时有两份 handoff 的完整 context，横向穿透发现"双重衰减模型"是新洞察）。

**关键洞察**：对正交板块+已知信息密度的场景，2 Agent + 主CC全权 是最优配置。主 CC 不需要 spawn QR——它在 context 中已经有全部素材。

**→ 下一步**：架构层面(S0)和流程层面(S1 Gate)都验证了。现在进入执行层面(S2)——Agent 在执行过程中怎么自我调节？

#### R15 `9bdf7df`: Heartbeat 协议

**为什么做**：CORAL 论文中 Heartbeat 禁用后性能 -18.6%。但 v6.0 精简时把它删了（当时认为"progress events 够了"）。问题是 progress events 只记录"做到哪了"，不记录"发现了什么/没发现什么/下一步去哪"——缺乏自我反思。

**设计**：两种信号：
- Reflect（每完成 1 个搜索方向）：`[REFLECT] 发现:{} / 未发现:{} / 下一步:{}`
- Pivot（连续 2 方向无新发现）：`[PIVOT] 原方向:{} → 新方向:{换关键词/换语言/换数据源}`

**结果**：2/2 Expert 正确执行。Expert-人格：4 次 Reflect + 1 次 Pivot(中文→英文)。标签格式使主 CC 监控从"读全文"降级为"grep 标签"。

**问题发现**：Heartbeat 需写入 spawn prompt 模板（仅 SKILL.md 描述不够，Agent 看不到）。这直接引出了下一轮的问题——spawn prompt 的哪些部分会被 Agent 忽略？

#### R16 `5874de9`: Spawn prompt 结构（Lost in Middle 验证）

**为什么做**：R15 中 Heartbeat 在 SKILL.md 描述但 1/3 Expert 没执行。是"没看到"还是"看到了但忽略"？Liu 2023 TACL 论文说中间位置信息丢失 20%+。如果放在 spawn prompt 中间段落呢？

**测试设计**：所有约束同时放在 front(前50字) + end("重申硬约束"段落)。对照：Heartbeat 仅放中间。

**结果（整个实验中最震撼的数据）**：

| 约束位置 | 合规率 | 解释 |
|----------|:------:|------|
| 前置 + 末尾重申 | **100%** (6/6) | 开头说一遍 + 结尾再强调一遍 = 全部执行 |
| 仅放中间段落 | **0%** (0/3) | 放在中间 = 等于没写 |

> 💡 **类比**：想象你给下属发一封很长的邮件。你在开头写了"周五前交报告"，结尾又写了"再次提醒：周五截止"——他一定记得。但如果这句话藏在第三段中间一个从句里？他大概率没看到。AI 的行为模式和人类读长文完全一样。

**这组实验在实际协作中复现了 Lost in Middle**：放在中间的约束 6 次都被忽略，移到首尾后 6 次都被执行。

**写入规则**：给 Agent 的任务指令必须遵循三原则——前 50 字放最关键约束，末尾用"重申硬约束："独立段落逐条列出，中间只放本轮特定的研究信息。

**→ 下一步**：执行层面解决了(Expert 可靠执行 + prompt 结构正确)。现在进入审查层面——什么情况下需要启动 deep debate？

#### R17 `e86b2d8`: 异议触发 + 解决分类

**为什么做**：R1-R16 所有研究中 QR 都是"标准模式"。但学术争议主题如果不 debate，可能漏过"伪平衡"（将不对称证据呈现为平等叙事）。什么条件下应该触发 deep debate？

**测试设计**：故意构造对立板块——"追求幸福为何适得其反" vs "追求幸福为何有效"。

**结果**：
- 条件 1(矛盾结论) + 条件 3(active学术争议，15个信号词) 正确命中
- Deep debate QR 找到 **2个P0(伪平衡)**——标准QR(R16同主题)找到0个。说明异议触发的核心价值 = 检出标准模式漏过的问题。

**更重要的发现（异议解决分类）**：

两板块看似"矛盾"，但分析后发现是**定义分歧**而非事实矛盾：
- 板块 1 的"pursuit" = VHS-Factor3 监控型（焦虑地追踪幸福指标，beta=-0.61）
- 板块 2 的"pursuit" = Prioritizing Positivity 行动型（选择令人愉悦的情境，beta=+0.44）

**它们操作化了同一个词的不同含义**。概念拆分后矛盾消失。

**写入 SKILL.md**：异议触发后第一步 = 判断矛盾类型：
- 定义分歧 → 概念拆分（最常见——两方在说不同的事）
- 事实矛盾 → 检查方法差异（真正的矛盾，需要追查谁的实验方法有问题）
- 层次差异 → 标注适用层次，不强行统一（宏观规律和微观个案不矛盾）

> 💡 **可复用的原则**：遇到两个专家结论相反时，先检查他们的定义和分析层次是否一致。R19 再次使用这套分类后，仍能区分定义分歧、层次差异和事实矛盾。

#### R18 `d8240f0`: 评估漏斗

**为什么做**：R17 用了 deep debate（完整模式），很重但发现了 P0。R13 全 H 板块只需 30 秒扫描就够。需要一个系统化的"审核深度决策"——什么时候用采样、什么时候用标准、什么时候用完整。

**设计**：基于 confidence 三档——H(A>80%+无争议信号词)→采样 / M→标准 / L(或异议触发)→完整。来源：AlphaEvolve 的 cheap→expensive 评估漏斗原则。

**测试设计**：混合 confidence 场景——遗传学=H(确定性知识) / 神经机制=M(证据参差)。

**结果**：
- H 板块采样：3 点/~2min，全通过，0漏检
- M 板块标准：9 点+3逻辑链/~8min，发现 1 精度注意(非P0)
- **H 板块节省 ~75% 审核时间，无质量损失**

**→ 下一步**：评估漏斗解决了"怎么审"。但还缺一个机制——Phase 2 审完、进 Phase 3 综合前，如果板块间有根本性分歧怎么办？

#### R19 `560a718`: 共识度检查

**为什么做**：如果两个板块对同一问题给出相反结论（一个说效果衰减，一个说效果持久），直接综合会变成"稀泥调和"。需要在综合前检测分歧程度。

**来源**：Self-Consistency 论文（>80%共识=可信）。

**测试设计**：对立板块——PPIs效果衰减(d↓35-42%) vs 持久性(神经可塑性+习惯66天)。

**结果**：
- 两板块均 confidence:H（各自证据充分）但结论方向相反
- 共识度 ~55%（<60%阈值）→ 正确触发分歧处理路径
- **关键洞察**：<60% 不等于"需要 debate"。需要先判断分歧类型！

应用 R17 的三分类：判定为**层次差异**——板块 1 是群体平均(ITT分析)，板块 2 是条件性个体(per-protocol分析)。不同分析粒度得出不同结论是正常的，不需要 debate，只需标注适用层次。

**写入 SKILL.md**：<60%路径从"自动回退 debate"改为"先 R17 分类 → 层次差异不需debate/事实矛盾追查方法/定义分歧概念拆分"。

这是一个**机制复用验证**——R17 的分类框架不仅适用于异议触发场景，也适用于共识度检查。

> 💡 **可复用的原则**：如果你发明了一个分析框架，试着在完全不同的场景下用一遍。如果它依然有效，说明你抓住了底层规律而不是表面模式。R17→R19 的复用验证就是这种"框架泛化测试"。

### R12-R19 的回溯模式总结（精细化融入的方法）

回头看这 8 轮，每次新增内容写入 SKILL.md 时不是简单"在末尾加一行"，而是遵循**精细化融入**原则：

1. **找到精确位置**——新规则应该在流程的哪个时间点被读到？（如"跨授粉"放在 S2 Spawn 步骤第 2 个 Expert 之前，不是放在文件开头或末尾）
2. **与上下文衔接**——新规则的触发条件是什么？和前后步骤有没有矛盾？
3. **保持最小改动**——每次 ≤15 行，不碰已验证有效的部分
4. **措辞可执行**——不写"考虑做 X"，写"当 Y 时，做 X"。AI 需要明确的 if-then 规则
5. **写明不适用条件**——任何规则都有边界，写清楚"什么时候不需要这样做"

这样融入的好处：已有流程不被打扰（v7.5 验证通过的部分完好无损），新机制有准确的触发时机（不会误触发或被遗漏）。

#### R20 `e219c3e`: 集成验证（自然触发率）

**为什么做**：R12-R19 每轮都在"故意设计极端场景来激活机制"——就像消防演习时故意点火来测试灭火器。现在需要验证：在**正常日子里**（不刻意制造紧急情况），这些机制是否正常待命而不误触发？

**测试设计**：选了一个普通主题（文化适应性），不做任何特殊设计，就像一个普通的周二下午正常使用。

**结果**：9 个机制中 6 个自然触发（该响应的响应了），3 个保持沉默（异议/停滞/分歧处理——因为这次研究确实没有这些情况）。

**0 误触发。0 遗漏。**

> 💡 **类比**：就像安装了 9 个不同类型的烟雾报警器。消防演习时 9 个全响了（R12-R19证明了它们能响）。但平时做饭时不会误响（R20 证明了它们不会误报）。这才是好的安全系统——需要时出现，不需要时安静。

#### R21 `c117fee`: 效率验证（速度底线）

**为什么做**：R20 耗时 36min（文化适应主题搜索分散）。在高密度学术主题下的速度底线是多少？

**结果**：25min（比 R20 快 31%）。分解：
- Phase 0: 5min（侦察不可压缩——影响板块划分质量）
- Phase 1: 12min（瓶颈=较慢 Expert，信息密集无需 Pivot）
- Phase 2: 3min（两板块均 H→采样模式）
- Phase 3: 5min（主 CC 直接写，context 已有全部素材）

**25min 是 2-Agent 配置的自然底线**。进一步优化空间有限。

**意外发现**：两个 Expert 的 token 消耗差异高达 34%（70.6K vs 53.5K）——直接原因是主题的"信息分散度"不同。韧性研究的文献跨越心理学、神经科学、创伤学多个抽象层次，搜索方向更散；PTG 则集中在临床领域。这意味着 **研究速度主要受主题特征控制，而非框架设计**——框架能做的是不添堵。

### 补充篇：v8.0-alpha 的结构添加轮 (R20-R31, 第一批次)

> **背景说明**：上面 R12-R21 讲的是每个机制的**验证过程**（第二批次，在 Desktop\2）。但在验证之前，这些机制首先要被**设计并写入 SKILL.md**——这是在第一批次（Desktop\1）中完成的。下面补充 R20-R31 的结构添加细节（对应 v8.0-alpha.9 到 alpha.19），每轮只做结构编辑+轻量审计，不跑完整研究。

#### alpha.9 (R20) `7c08aff`: Handoff 元数据头——让质检读 1 行就够

**问题**：Gate 1.5 覆盖审计时，主 CC 要读 3 份完整 handoff 才能判断哪个板块需要补充。能不能更快？

**设计**：Handoff 首行加结构化元数据：`[角色] [板块] [字数] [来源比例] [置信度:H/M/L]`。主 CC 只读 3 行首行就知道全局情况。

**精细化融入位置**：S3 Handoff 质量红线之后——不改 handoff 正文规则，只加首行要求。

#### alpha.10 (R21) `958c6ae`: 压缩提质原则——把"压缩不丢信息"从经验变成规则

**来源**：R3 和 R5 都验证了"压缩=提纯"（200字>500字、不读原文>读原文），但 SKILL.md 里没有明确把这个原则写出来。

**设计**：在 S3 通信规则中写明——"handoff ≤200 字是质量优化而非妥协；Expert 内部产出无限制，但传递给下游的只能是 filtered 精华"。

**为什么要显式写出来**：因为新的主 CC（每次启动都是"新人"）可能会觉得"200 字太少了吧，我应该让 Expert 写详细点"——这条规则防止它凭直觉推翻经过验证的参数。

#### alpha.11 (R22) `a3b238e`: 4 元素 Spawn 检查清单

**来源**：Codex AGENTS.md 的"任务委派四要素"。每个 spawn prompt 必须包含：(1) 目标 (2) 产出格式 (3) 可用工具 (4) 任务边界("不做什么")。

**为什么"不做什么"特别重要**：实验中发现 Agent 天然倾向于扩展覆盖范围——你让它研究"剂量效应"，它可能顺手写了"组织应用"。显式禁止（"不研究 X 板块的内容"）比隐性期望（只给标题暗示范围）有效得多。验证结果：3/3 Expert 零越界。

#### alpha.12 (R23) `0c9bba8`: 共识度检查

**设计**：Phase 3 综合前，主 CC 对所有 handoff 核心结论做一致性评估。>80% → 直接综合 | 60-80% → 报告中标注分歧 | <60% → 先分类再决定是否 debate。

**与 R17 的衔接**：<60% 路径复用了 R17 的三分类框架（定义分歧/事实矛盾/层次差异），不另造轮子。

#### alpha.13 (R24) `8545d1d`: 学习触发——把"失败也是数据"制度化

**设计**：四种事件触发写入 learning-log：搜索全部失败→ERR | Agent 被接管→ERR | 意外高质发现→LRN | 跨板块矛盾→LRN。每条 ≤50 字。

**为什么要制度化**：之前 learning-history 的写入全靠"结束时想起来才写"，导致很多实战经验没被记录。固定触发条件 = 不依赖记忆力。

#### alpha.14 (R25) `b1a40aa`: 异构模型建议

**设计**：搜索/初步提取 → 用便宜模型(Haiku/Flash)；综合/验证/关键判断 → 用强模型(Opus/Pro)。主 CC 始终用最强模型。

**为什么是"建议"不是"规则"**：模型选择受用户环境限制（有些人只有某个模型的权限），写死不现实。但标注了"模型差异解释 15% 性能方差"让用户知道这个选择有代价。

#### alpha.15 (R26) `fda18eb`: 关键路径并行决策——不是所有事都值得并行

**设计**：问自己"这 N 个子任务中最长的是否 > 串行总时间/N？"是 → 并行（有缩短）；否 → 串行更划算（省 spawn 开销）。

**来源**：Kimi PARL 论文的关键路径公式 + R12 序贯策略的实战经验。

#### alpha.16 (R27) `99ff77b`: 验证独立性——同一件事不能让同一组人验证两次

**设计**：不同 Expert 必须用不同关键词/数据源验证同一 claim。共享搜索结果 = 失去验证价值。

**来源**：BrowseComp 论文发现"eval contamination"风险高达 3.7x。就像考试——两个学生抄了同一份答案，即使都写了"正确答案"，也不能算"两个独立验证"。

#### alpha.17 (R28) `41665be`: MAS 决策树——把 S0 三问变成快速路径

**设计**：4 个 if-then 判断——(1) 问题开放？→ MAS+共享记忆 (2) 答案可验证？→ Best-of-N 投票 (3) 上下文>50K？→ 分解式 MAS (4) 需要完整性？→ 加覆盖审计。全否 → SAS 就够。

**为什么做**：S0 的"三问"太抽象，每次启动主 CC 要"思考"怎么应用。改成决策树后变成 pattern matching——快得多。

#### alpha.18-19 (R29-R31): ROI 审计 + 集成测试

**R29-R30**（`1699baa`）：回顾 alpha.1-17 所有新增内容，逐条评估 ROI。结论：17 个机制全部保留（没有一个是"听起来有道理但实际没用"的——因为每个都有论文数据支撑且位置精确）。

**R31**（`9d68934`）：用全新主题"AI Agent 协作中的信任校准机制"跑端到端测试。**16/18 可触发钩子正确工作**（89%），2 个未触发因环境限制（非设计问题）。0 误触发。

**→ 结论**：v8.0 正式发布（`e07a16c`）。

| v8.7 | R18 | 评估漏斗 | H 板块省 75% 审核时间 | 否（按预期工作） |
| v8.8 | R19 | 共识度 | <60% 正确触发 + R17 框架复用 | 是（改 <60% 路径） |
| v8.9 | R20 | 集成 | 6/9 触发 0 误触发 | **否**（首次无需改动） |
| v8.9 | R21 | 效率 | 25min 底线确认 | **否**（连续第 2 轮无改动） |

**模式**：R12-R19 每轮都微调了 SKILL.md（改进轮），R20-R21 不需要任何改动（验证轮）。连续 2 轮无改动 = 系统稳定。

## 为什么从 R20 之后决定定稿

用户在 R20 之后指出了一个关键洞察：

> "你从 R20 开始做的工作不是在改进 skill——是在确认 skill 已经对了。验证轮和改进轮是两件事。"

回顾 R12-R21：
- R12-R19：每轮发现问题并修改 SKILL.md（**改进轮**——像调琴，每次转一下螺丝）
- R20-R21：运行完毕后 SKILL.md 无需任何修改（**验证轮**——弹一首曲子，音准全对）

当连续 2 轮验证都不需要任何改动时，说明系统已经稳定——就像调完琴后连弹两首曲子都不走音，说明可以上台了。**继续跑轮次只是在花钱确认已知结论。**

于是决定：v8.9 升级为 v9.0（定稿版）。不再加新机制，不再跑验证轮。453 行是最终形态。

## 关键设计决策汇总（为什么 v9.0 长这样）

| 设计选择 | 通俗解释 | 为什么这样决定 |
|----------|---------|---------------|
| 扁平星型(无PM) | 老板直接管员工，没有中层 | 中层传话在实验中每次都断线(4个项目全失败) |
| ≤5 Agent硬限 | 最多雇5个人 | 5人接力，每人90%准确→整体只有59%(数学决定的) |
| 默认2-3 Agent | 一般只派2-3人 | 实验证明2人配置省38%成本且质量不降(R14) |
| Handoff 150-200字 | 交班条不超过200字 | 200字=500字的信息量(压缩去掉废话后信息密度更高) |
| 主CC直接综合 | 老板自己写终稿 | 老板已经看完所有材料了，再请人写反而多花5分钟+4万token |
| Spawn首尾约束 | 重要话开头说+结尾再说 | 放中间=AI 100%看不到(R16实验数据) |
| 异议后先分类 | 发现"矛盾"先判断是真矛盾还是在说不同的事 | 大多数"矛盾"其实是同一个词的不同含义(R17+R19) |
| Gate 1.5是安全网 | 质量好时30秒通过，差时才细查 | 不是每次都搞大检查，而是有问题时才启动(R13) |
| 评估漏斗三档 | 确定的快速扫、模糊的仔细查、争议大的全面审 | 确定性高的板块省75%审核时间(R18) |
| <60%先分类再决定 | 意见不统一时先看是哪种不统一 | "不同分析粒度"不需要辩论，标注清楚就行(R19) |
| foundations/分层 | 操作手册和百科全书分开放 | 彻底解决"精简就丢知识"的死循环(v5.0-v6.3的惨痛教训) |

## 如果你只记住三件事

1. **Agent 数量要受任务约束**：每多一个交接环节，就多一次出错机会。当前实验里，2-3 个 Agent 最稳定。
2. **关键约束放在首尾**：同一条约束放在中间时 0/6 执行，移到首尾后 6/6 执行。
3. **操作手册和知识档案分开**：SKILL.md 保持简短，设计依据和实验记录放在单独文件中。
